# clixz 2.3 — appliquer les plans, démon géré par le paquet, todo

Validé le 2026-10-06. Complète `REFONTE.md` et en renverse une décision (§9 :
« le MCP produit le plan, l'humain exécute au clavier »).

## 0. Ce qui change, en une phrase chacun

1. Un plan préparé par l'IA peut être **appliqué** depuis le MCP, après ton accord
   dans le client Claude — création, modification, correction, archivage d'un
   service.
2. Le paquet installe et tient à jour **ses propres unités systemd** ; le démon
   se relance seul quand la version change.
3. Une **todo** (titre, description, état) partagée entre la CLI et l'IA.
4. `exposed` lit la base du proxy **au moment de l'appel** : plus de timer.
5. `clixz upgrade` installe **la dernière version publiée**, sans cache.
6. Des **ressources MCP** en plus, pour qu'un projet Claude ait un contexte à jour.
7. Un `new` appliqué **crée la stack dans Komodo**, préconfigurée, sans la
   déployer.

## 1. Décisions

| Question | Décision |
|---|---|
| Qui valide un apply ? | Toi, dans le client Claude : `plan_apply` est un outil à part, laissé sur « demander à chaque fois ». |
| Qui déploie ? | Komodo, comme aujourd'hui. clixz écrit les fichiers et **crée la stack** (§7 bis) ; le déploiement et l'environnement restent à toi, dans Komodo. |
| Ce que l'IA peut appliquer | `new` (avec son compose et son service.yaml), `edit`, `fix`, `rm` (archivage). Catégories et dépôts restent des plans non applicables. |
| `.env` | Jamais écrit par un plan. `new` crée un `.env` vide ; Komodo le remplit. |
| Todo | L'IA a les mêmes droits que toi : créer, modifier, supprimer. Fichier lisible par tous. |
| `exposed` | Lecture directe de la base NPM à chaque appel, par le processus root (§2). Le timer `clixz-snapshot` disparaît. |
| Dépôt du serveur MCP | `/opt/images/mcp-clixz`, remote `Coxyz/ClixzMCP`, poussé sur `main`. |

## 2. Architecture

```
IA ─▶ mcp-clixz (conteneur, Auth0) ─▶ clixz-mcpd (svc_mcprun, lecture seule)
                                          │  lectures : CLI non privilégiée, inchangé
                                          │  plan / apply / plans / exposed / écritures todo
                                          ▼
                             /run/clixz-apply.sock   (root:svc_mcprun 0660)
                                          ▼
                    clixz-apply@.service — un processus root par requête
                    (activation par socket ; rien ne tourne en permanence)
```

- **`clixz-apply`** est le seul processus qui écrit pour le compte de l'IA. Il
  relit et revalide chaque requête : il ne fait aucune confiance à `clixz-mcpd`.
  Sandbox systemd : écriture limitée à `/srv/docker`, `/var/lib/clixz` et au
  fichier manifest ; capacités `CHOWN FOWNER DAC_OVERRIDE DAC_READ_SEARCH` ;
  réseau limité aux adresses locales et aux réseaux Docker
  (`IPAddressDeny=any`, `IPAddressAllow=localhost 172.16.0.0/12`) — juste de quoi
  joindre Komodo Core ; `NoNewPrivileges`.
- **Le conteneur ne voit pas cette socket** : seul `/run/clixz-mcpd` y est monté.
  `clixz-mcpd` garde `ProtectSystem=strict` et n'écrit rien lui-même : il relaie.
- **Journal** : chaque plan, apply, suppression de plan et écriture de todo
  laisse une ligne `[clixz-apply] …` (id, action, cible, résultat) dans le
  journal de l'unité.

### Protocole de `clixz-apply`

Une ligne JSON en entrée, une ligne JSON en sortie (comme `clixz-mcpd`).

| `cmd` | Paramètres | Effet |
|---|---|---|
| `plan` | `action` ∈ new/edit/fix/rm, `service`, `compose?`, `service_yaml?`, `stack?` (new) | calcule, refuse ou enregistre ; renvoie le plan |
| `apply` | `plan_id` | recalcule, compare, exécute |
| `plans` | — | plans en attente (et expirés depuis moins de 24 h) |
| `plan-show` | `plan_id` | un plan complet |
| `plan-drop` | `plan_id` | supprime un plan en attente |
| `exposed` | — | même JSON que `clixz exposed --json` |
| `todo-add` / `todo-edit` / `todo-rm` | voir §5 | écrit la todo |

Limites : requête ≤ 512 Kio, `compose` ≤ 128 Kio, `service_yaml` ≤ 32 Kio,
`plan_id` = 8 caractères hexadécimaux.

## 3. Plans

### Calcul

`compute_plan(config, request)` produit, sans rien écrire :

- `commands` : les commandes, pour lecture (les horodatages apparaissent comme
  `<timestamp>`) ;
- `diff` : diff unifié de `compose.yaml` et `service.yaml` (contre l'existant,
  ou contre rien pour `new`) ;
- `lint` : le lint du compose **résultant**, après `ignore.yaml` ;
- `blocked` : les raisons de refus. Non vide → aucun id, rien d'enregistré ;
- `fingerprint` : l'empreinte de ce qui doit être vrai au moment de l'apply.

| Action | Bloqué si | Empreinte |
|---|---|---|
| `new` | service existant ; compte de la catégorie absent ; compose ou service.yaml invalide ; erreur de lint non acceptée | requête + « chemin absent » |
| `edit` | service absent ; ni compose ni service.yaml fournis ; contenu identique ; invalide ; erreur de lint non acceptée | requête + sha256 des fichiers remplacés |
| `fix` | rien à corriger | liste triée des corrections |
| `rm` | service absent | requête + « chemin présent » |

« Erreur de lint non acceptée » = un constat de niveau `error` dans `lint.yaml`
qu'aucune entrée d'`ignore.yaml` ne couvre pour ce service (`privileged`,
`network_mode: host`, `docker.sock`, `/` monté, `/etc/clixz` en écriture…).
L'IA ne peut modifier ni l'un ni l'autre : elle ne peut pas se donner root par
un compose.

`service.yaml` est validé par `parse_meta` : une erreur dure bloque, un
avertissement est rapporté.

### Stockage

`/var/lib/clixz/plans/<id>.json`, dossier `root:root 0700`, fichier 0600. L'id
est aléatoire (`secrets.token_hex(4)`). Comme seul root écrit dans ce dossier,
l'IA ne peut pas fabriquer un plan : pas besoin de signature. Validité : une
heure. Les plans expirés restent listés 24 h (état `expired`) puis sont purgés
à la création suivante.

### Application

1. Réclamer le plan par `rename(<id>.json → <id>.applying)` : deux apply
   simultanés du même plan, un seul gagne.
2. Refuser s'il a expiré.
3. Recalculer depuis la requête enregistrée et l'état actuel du disque ;
   refuser si l'empreinte diffère ou si le plan est désormais bloqué
   (« l'état a changé depuis le plan — refais-le »).
4. Exécuter : `create_service` / `edit_service` / `apply_fixes` /
   `archive_service`. `edit` copie d'abord l'ancien fichier sous
   `.archive/<cat>/<svc>/updates/` (mécanisme existant).
5. Si un `service.yaml` a changé (`new`, `edit` avec service.yaml, `rm`) :
   régénérer `manifest.json`. Un manifest en erreur n'annule pas l'apply ; il
   est signalé.
6. Supprimer le plan (usage unique) ; journaliser.

### CLI

- `clixz new apps/x [--compose F] [--service-file F]` : `-` = entrée standard ;
  sans fichier, le gabarit comme aujourd'hui.
- `clixz edit apps/x [--compose F] [--service-file F]` : nouveau verbe.
- `--plan` garde son sens : afficher, ne rien écrire, ne rien enregistrer.
  Les deux verbes interactifs bloquent sur les mêmes raisons que `blocked`.
- `clixz plan ls | show <id> | apply <id> | drop <id>` : les plans préparés
  par l'IA, vus ou appliqués depuis le terminal (root, via sudo).

## 4. Démon géré par le paquet

Les unités quittent `deploy/` pour `src/clixz/systemd/` (données du paquet) :
`clixz-mcpd.service`, `clixz-apply.socket`, `clixz-apply@.service`.

`sudo clixz daemon install [--plan]` :

1. crée le compte `svc_mcprun` s'il manque ;
2. crée `/var/lib/clixz` (`root:<state.group> 2775`), `plans/` (0700) et
   `todo.yaml` (0664) ;
3. crée le fichier manifest s'il manque (il doit exister pour être rendu
   inscriptible au processus root) ;
4. rend les unités — `SupplementaryGroups` de `clixz-mcpd` = les groupes de
   toutes les catégories du config ; chemin du manifest depuis le config — et
   n'écrit que celles qui diffèrent ;
5. retire les unités d'avant (`clixz-snapshot.*`, et `clixz-admind`,
   `clixz-runnerd` si elles traînent) et `/etc/clixz/npm-hosts.json` ;
6. `daemon-reload`, `enable --now clixz-mcpd.service clixz-apply.socket`,
   redémarre `clixz-mcpd` si son unité a changé.

`clixz daemon status [--json]` (sans sudo) : pour chaque unité, installée ou
non, conforme au paquet ou non, active ; et si `clixz-mcpd` a démarré avant la
dernière installation du paquet (il sert alors l'ancien code).
`sudo clixz daemon restart` : redémarre `clixz-mcpd`.

**Relance automatique** : `clixz-mcpd` relit toutes les 30 s la version
installée (`importlib.metadata`). Si elle diffère de celle qu'il a chargée, il
s'arrête proprement et systemd le relance (`Restart=always`). Ça couvre une mise
à jour faite par n'importe quel chemin, `pipx` à la main compris.
`clixz-apply` n'a pas ce problème : un processus neuf par requête.

`clixz category add` rappelle `sudo clixz daemon install` dans ses étapes
suivantes : c'est lui qui ajoute le groupe de la catégorie au démon.

## 5. Todo

Fichier `/var/lib/clixz/todo.yaml`, `root:docker 0664` dans un dossier
`2775` : lisible par tous, modifiable sans sudo par les membres de `docker`
(l'opérateur). clixz réimpose ces droits quand il écrit en root. Écriture en
place sous `flock`, donc propriétaire et mode préservés.

```yaml
next_id: 3
items:
  - id: 1
    title: Sauvegardes restic
    state: todo            # todo | doing | done | archived
    created: 2026-10-06T19:00:00Z
    updated: 2026-10-06T19:00:00Z
    description: |
      Support externe, timer systemd, test de restauration.
```

CLI : `clixz todo ls [--state S …] [--all] [--json]` (par défaut : `todo` et
`doing`), `add TITRE [-d TEXTE] [--state S]`, `show ID`,
`edit ID [--title] [-d] [--state]` (sans option : `$EDITOR`), `start ID`,
`done ID`, `archive ID`, `rm ID`.

Côté MCP : lectures par la CLI non privilégiée (`todo`, `todo-show`), écritures
relayées à `clixz-apply` (`todo-add` : `title`, `description?`, `state?` ;
`todo-edit` : `id`, `title?`, `description?`, `state?` ; `todo-rm` : `id`).
Pas de plan pour la todo.

Config, nouvelle section facultative :

```yaml
state:
  dir: /var/lib/clixz   # plans/ (root seul) et todo.yaml (lisible par tous)
  group: docker         # qui peut éditer la todo sans sudo
```

## 6. `exposed` en direct

- `clixz exposed` lit la base en root : la CLI passe par sudo si besoin.
- Côté MCP : `exposed` est relayé à `clixz-apply`, qui lit la base au moment de
  l'appel (`ReadWritePaths` couvre `/srv/docker`, où SQLite en mode WAL peut
  devoir créer son `-shm`) et liste les conteneurs par la socket Docker.
- Supprimés : `--snapshot`, `read_snapshot`, `npm.snapshot` (clé retirée, avec
  message de migration), les unités `clixz-snapshot.*`, `npm-hosts.json`.
- Le manifest n'est plus rafraîchi toutes les 15 min mais à chaque apply qui
  touche un `service.yaml`. Une édition à la main demande `sudo clixz manifest`.

## 7. `clixz upgrade`

1. Demander à PyPI la dernière version (`/pypi/clixz/json`, `Cache-Control:
   no-cache`). Déjà à jour → le dire et s'arrêter.
2. Mettre à jour sans cache : `pipx upgrade --pip-args=--no-cache-dir clixz`
   (`--global` si besoin), ou `uv tool upgrade --no-cache clixz`.
3. Vérifier la version installée. Si elle est encore en retard (index de PyPI
   pas encore propagé), réessayer jusqu'à 3 fois à 15 s d'intervalle, puis
   échouer en le disant.
4. Si les unités sont installées : lancer `clixz daemon install` **du nouveau
   binaire**, qui met à jour les unités et redémarre le démon.

## 7 bis. Stack Komodo créée avec le service

Komodo déploie déjà tout depuis `/srv/docker`, que Periphery voit en
`/services`. Un `new` appliqué ajoute une étape après l'écriture des fichiers :

```
POST <komodo>/write/CreateStack     X-Api-Key / X-Api-Secret
{"name": "<stack>",
 "config": {"server_id": "<serveur>", "files_on_host": true,
            "run_directory": "/services/<cat>/<svc>"}}
```

- Nom de la stack : le nom du service par défaut (la convention actuelle), ou
  le champ facultatif `stack` de la requête `new`.
- Rien d'autre : pas de `environment` (le `.env` reste à toi), pas de
  déploiement. La stack apparaît dans Komodo, prête à être complétée puis
  déployée.
- Une stack du même nom existe déjà → étape sautée, signalée. Komodo
  injoignable ou en erreur → les fichiers restent créés, l'apply réussit avec un
  avertissement qui dit quoi faire à la main.
- `rm` ne touche pas à Komodo : il signale que la stack y reste.
- Le plan affiche l'étape (`komodo: CreateStack …`) ; il ne contacte pas
  Komodo, l'apply si.

Config, section facultative ; sans elle, l'étape est absente :

```yaml
komodo:
  credentials: /etc/clixz/komodo.toml   # key, secret, url facultative — root 0600
  server: boxyz          # nom ou id du serveur Komodo (défaut : le seul existant)
  container: komodo-core # sans url : IP de ce conteneur, port 9120
  run_root: /services    # où Periphery voit root_dir
```

La clé d'API est celle d'un **utilisateur de service Komodo** dédié, non
administrateur, avec juste le droit de créer des stacks sur ce serveur. Seul
root (donc `clixz-apply`) lit le fichier ; ni `clixz-mcpd` ni le conteneur.

## 8. Serveur MCP (`Coxyz/ClixzMCP`)

Outils :

| Outil | Nouveau | Rôle |
|---|---|---|
| `service_create(service, compose?, service_yaml?, stack?)` | modifié | plan `new` (+ stack Komodo) |
| `service_update(service, compose?, service_yaml?)` | oui | plan `edit` |
| `service_fix(service?)`, `service_delete(service)` | modifiés | plans `fix`, `rm` |
| `plan_list`, `plan_read(plan_id)`, `plan_delete(plan_id)` | oui | plans en attente |
| `plan_apply(plan_id)` | oui | exécute — annotation `destructiveHint` |
| `todo_list(state?, all?)`, `todo_read(id)` | oui | lecture |
| `todo_create`, `todo_update`, `todo_delete` | oui | écriture |
| `service_exposed` | modifié | lecture en direct |

Les outils de lecture portent `readOnlyHint`. Les instructions du serveur
disent : montrer le plan (diff, lint), attendre l'accord explicite, puis
`plan_apply` ; ne jamais affirmer qu'un plan est appliqué sans le résultat de
`plan_apply` ; le déploiement se fait dans Komodo ; consulter `todo_list` en
début de conversation sur l'infra.

Ressources — le schéma `coxyz://` devient `clixz://` (les ressources jointes à
un projet Claude sont à rattacher) :

| Ressource | Contenu |
|---|---|
| `clixz://overview` | **nouvelle** — synthèse Markdown : catégories, services (image, URL), exposition, résumé de l'audit, todo ouverte, plans en attente. Celle à joindre à un projet. |
| `clixz://todo` | **nouvelle** — todo ouverte (Markdown) |
| `clixz://plans` | **nouvelle** — plans en attente |
| `clixz://rules` | **nouvelle** — règles de compose et écarts acceptés |
| `clixz://exposed` | **nouvelle** — exposition réelle |
| `clixz://check` | **nouvelle** — résumé de l'audit |
| `clixz://categories`, `clixz://services`, `clixz://service/{name}`, `clixz://config`, `clixz://docs`, `clixz://doc/{name}` | existantes, renommées |

Nettoyage au passage : repli `/run/clixz-runner`, variables `COXYZ_*`, noms
`coxyz` dans les logs, le README et le Dockerfile.

## 9. Sécurité — ce qui reste vrai, ce qui change

- Le chemin Internet → Auth0 → écriture root dans `/srv/docker` **existe
  désormais**. Il est borné par : l'approbation de `plan_apply` dans le client ;
  un plan que seul root peut enregistrer ; le recalcul à l'apply ; le refus des
  erreurs de lint non acceptées ; l'absence d'écriture du `.env`, du config, de
  `lint.yaml`, d'`ignore.yaml` ; l'absence de destruction (`rm --force` et
  `repo rm` restent au clavier).
- Un compose écrit par l'IA n'est **pas déployé** par clixz : il faut une action
  dans Komodo. La clé Komodo de clixz ne sert qu'à créer des stacks ; elle
  appartient à un utilisateur de service sans droit d'administration.
- `clixz-mcpd` ne gagne aucun droit d'écriture.
- Durcissement possible plus tard, hors périmètre : exiger un scope Auth0 dédié
  pour `plan_apply` et les outils d'écriture.

## 10. Tests

- `plans` : calcul (blocages, diff, lint), empreinte, péremption, plan modifié
  entre plan et apply, double apply, purge — sur une arborescence temporaire,
  `chown` simulé.
- `todo` : ajout, modification, états, suppression, `next_id`, fichier absent,
  verrou.
- `applyd` : validation (actions, regex, tailles, types), dispatch.
- `mcpd` : routage relais / CLI / plan non privilégié, relance sur changement
  de version.
- `daemon` : rendu des unités (groupes, chemin du manifest), détection d'écart.
- `upgrade` : lecture de PyPI, arguments sans cache, nouvelle tentative.
- `komodo` : construction de la requête, résolution du serveur et de l'URL,
  stack déjà existante, erreurs — `urlopen` simulé.
- Aucun conteneur lancé sur Boxyz pour tester.

## 11. Mise en service

1. PR, CI, merge ; release 2.3.0 par release GitHub.
2. Sur l'hôte : `sudo clixz upgrade`, puis `sudo clixz daemon install`.
   Dans Komodo : un utilisateur de service `clixz` et sa clé d'API, posée dans
   `/etc/clixz/komodo.toml` ; puis lecture d'une stack existante pour vérifier
   les réglages par défaut à reproduire.
3. Image `mcp-clixz` reconstruite (mémoire vérifiée avant), redéployée dans
   Komodo ; vérifier les outils de bout en bout.
4. Par le MCP : bascule des `.env` en `root:docker 640` (édition du config par
   toi, puis `service_fix` + `plan_apply`, puis test d'un redéploiement Komodo) ;
   import de `docs/TODO-OPXYZ.md` dans la todo ; passe sur les `service.yaml` et
   chasse aux vestiges, chaque correction en plan.
