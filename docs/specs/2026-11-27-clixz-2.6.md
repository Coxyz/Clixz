# clixz 2.6 : lecture du runtime Docker par le MCP

Date : 2026-11-27. Todo : #36 (logs), #46 (opxyz hors de `docker`), #49 (résumé de compose).

## Pourquoi

Le MCP voit la config (compose, service.yaml), l'audit et l'exposition, pas ce qui tourne. Un
diagnostic (un conteneur qui redémarre, unhealthy, qui touche son `mem_limit`) oblige aujourd'hui à
passer par SSH. Depuis le 2026-11-27, `opxyz` n'est plus dans le groupe `docker` : même les sessions
d'agent sur l'hôte ne voient plus Docker sans mot de passe. Le MCP doit donc lire le runtime par un
chemin contrôlé.

## Ce que l'opérateur a décidé

- Toutes les commandes clixz de la CLI se lancent avec `sudo`. Il n'y a pas de lecture sans mot de
  passe : l'opérateur n'est dans aucun groupe `svc_*` ni dans `docker`.
- Pour les logs, il a choisi l'option (b) : seuls les services autorisés explicitement ont leurs logs
  lisibles.

## Choix de construction (à vérifier par l'opérateur)

1. **Liste des logs autorisés dans `/etc/clixz/config.yaml` (`docker.logs`)**, pas dans
   `service.yaml`. `service.yaml` peut être réécrit par un plan MCP : l'IA pourrait se proposer
   l'accès aux logs de bitwarden, et une approbation donnée trop vite suffirait. `config.yaml` n'est
   modifiable qu'à la main, en root, comme l'acceptation d'une règle de niveau error.
2. **Un processus dédié, `clixz-inspect`**, plutôt que d'étendre `clixz-apply`. `clixz-apply` est root,
   a `CAP_DAC_OVERRIDE` et écrit dans `/srv/docker`. Une lecture n'a besoin d'aucun de ces droits, et un
   bug de lecture ne doit pas tomber dans un processus qui écrit.
3. **`DynamicUser=yes` + `SupplementaryGroups=docker`**, pas `User=root`. Le socket Docker équivaut à
   root, quoi qu'on fasse : si le code est compromis, l'API Docker est ouverte. Mais un compte
   dynamique ne lit pas les fichiers de root (`/etc/shadow`, `komodo.yaml`, les `.env`) et n'écrit
   nulle part. Aucune capability, `PrivateNetwork=yes`, `ProtectSystem=strict`. Un processus est lancé
   par requête et s'arrête ensuite.
4. **L'API Engine en GET seulement**, par `http.client` sur le socket Unix (stdlib). Le client n'a pas
   de méthode pour POST, PUT ou DELETE, et les chemins viennent d'une liste fermée. Le CLI `docker`
   n'est pas utilisé.

## Masquage des logs (au mieux)

Le masquage réduit l'exposition des logs, il ne la supprime pas : c'est pour ça que l'accès se fait
service par service. On applique, dans l'ordre :

1. Les **valeurs de l'environnement du conteneur** (lues par l'API, jamais renvoyées) : chaque valeur
   d'au moins 8 caractères, ou d'au moins 3 caractères si le nom ressemble à un secret, est remplacée
   par `[masqué:NOM]`.
2. Les motifs : `Authorization:`, les identifiants dans une URL (`user:pass@`), `clé=valeur` ou
   `clé: valeur` quand la clé ressemble à un secret, les JWT, les blocs de clé privée PEM, et les
   jetons opaques d'au moins 40 caractères (sauf l'hexadécimal pur, qui correspond aux identifiants et
   empreintes).
Les séquences ANSI et les caractères de contrôle sont retirés AVANT le masquage : une séquence placée
entre une clé et son `=` cacherait la paire. Les descriptions d'outils disent au modèle que le
contenu est une donnée.

## Revue de sécurité

- **Frontière** : un nouveau chemin Internet → MCP → `clixz-mcpd` → `clixz-inspect` (groupe
  `docker`). Il accepte une liste fermée de 5 requêtes, revalidées par `clixz-inspect` : nom de
  conteneur `^[A-Za-z0-9][A-Za-z0-9_.-]{0,127}$`, encodé dans l'URL, et `tail`/`since` entiers bornés
  (un `bool` est refusé). Le socket est `root:svc_mcprun 0660`, il n'est pas monté dans le conteneur.
- **Risque résiduel accepté** : une exécution de code dans `clixz-inspect` donne l'API Docker, donc
  root. C'est le même risque que n'importe quel lecteur de socket (Portainer, Homepage, un proxy de
  socket). Ce qui le limite : stdlib seulement, aucun parseur exotique (JSON de dockerd), un processus
  par requête, `MemoryDenyWriteExecute`, `SystemCallFilter=@system-service`.
- **Secrets** : voir les colonnes « jamais renvoyé ». Les tests vérifient qu'aucune valeur d'`Env` ni
  de `Cmd` ne ressort, même dans un message d'erreur.
- **Décision opérateur** : `docker.logs` n'est modifiable que dans `config.yaml`, à la main.
- **Déni de service** : les sorties sont bornées. Les stats de tous les conteneurs se lisent avec
  4 fils au plus. `RuntimeMaxSec=60`, `MaxConnections=4`.

## Hors périmètre

`docker exec`, redémarrer, toute écriture : jamais par ce chemin. Les redémarrages restent dans
Komodo.
